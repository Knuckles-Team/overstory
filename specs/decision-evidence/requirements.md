# OVERSTORY-DECIDE requirements

| ID | Requirement | Verification |
|---|---|---|
| `OVERSTORY-DECIDE-R001` | **Evaluation dashboard shows calibration and coverage.** A dashboard presents decision evaluation calibration and coverage metrics — cohort, sample count, source class, evaluation window, target versus observed coverage, risk, and receipt version — as independently labeled fields, and shows no numeric coverage, calibration or deployment claim when the evaluation is synthetic-only, missing or underpowered. | Independent-label fixture tests plus negative fixtures for the synthetic-only, missing, and underpowered cases. |
| `OVERSTORY-DECIDE-R003` | **Decision explorer cites premises, derivations and certificate.** A typed decision explorer renders the chosen and excluded options for a decision. It cites the premise and derivation identifiers, the certificate and any violations that applied. | Contract fixture and rendered route tests. |
| `OVERSTORY-DECIDE-R004` | **Why-not explanations run on demand within a bounded budget.** A why-not explanation is computed on demand within a bounded solve budget. The reader sees any timeout or refusal. It never alters the original decision record. | Timeout and refusal integration fixture tests. |
| `OVERSTORY-DECIDE-R005` | **Dashboard labels each evaluation field independently.** The evaluation dashboard labels cohort, sample count, source class, evaluation window, target and observed coverage, risk, and receipt version as separate, independently sourced fields rather than a single combined claim. | Independent-label fixture and rendered dashboard tests. |
| `OVERSTORY-DECIDE-R006` | **No coverage claim shown for inadequate evaluation data.** The dashboard shows no numeric coverage, calibration or deployment claim when the underlying evaluation is synthetic-only, missing, or underpowered. | Negative fixture tests for each of the synthetic-only, missing, and underpowered cases. |
| `OVERSTORY-DECIDE-R007` | **Tenant or purpose change invalidates cached decision queries.** Changing tenant or purpose invalidates any cached decision or evaluation query. A stale response never overwrites a result from a newer selection. | Two-tenant browser test exercising cache invalidation and stale-response ordering. |
| `OVERSTORY-DECIDE-R008` | **Explanation views work without color, hover or pointer.** Every part of the decision explanation structure is usable without relying on color alone, hover-only reveal, or pointer-only controls. | Keyboard and accessibility tests covering the full explanation structure. |
| `OVERSTORY-DECIDE-R002` | **Decision explorer surfaces premises, derivations and violations.** The decision explorer presents a selected decision's premise classes, derivations, certificate, why-not explanation and violations through the WebUI. Typed calls to the Arbora read API back it. | Component tests cover the explorer's rendering logic, plus a browser integration test against an authenticated Keycloak-backed Arbora session. |
| `OVERSTORY-DECIDE-R009` | **Proposal review view (rollup).** The proposal review view must list proposals of `MEDULLA-SDLC-R017` for a project. It must read them only through the arbora operation of `ARBORA-OPS-R896.5`. Each proposal shows its kind, its target, its evidence and its gate results. The view never writes a spec, a plan or a task. Children `.1` to `.3` deliver it. Depends on: ARBORA-OPS-R896.5, MEDULLA-SDLC-R017.2. | Satisfied only when every child is satisfied. Root journey: `src/components/views/__tests__/ProposalReview.e2e.test.tsx::test_reviewer_lists_and_decides_a_proposal` (L4). |
| `OVERSTORY-DECIDE-R009.1` | **Typed kinds and evidence.** The view must group proposals by kind. The kinds are add, update, split, prune and retire a row. Other kinds edit a plan section, change a task, add a contract, resolve a clarification or tune a knob. Each proposal must show its evidence: code-graph facts, research citations and gate results. A kind or evidence class that is missing shows `unavailable`. The view invents no text. File: `src/components/views/ProposalReview.tsx`. | Test: `src/components/views/__tests__/ProposalReview.test.tsx::test_kinds_and_evidence_render_and_missing_is_labeled` (component). |
| `OVERSTORY-DECIDE-R009.2` | **Accept and reject land only as a pull request.** An accept action must request the pull request through `ARBORA-OPS-R896.5`. The view then shows the pull request link and its gate state. A reject action records the refusal through the same operation. The view offers no path that writes a file or merges. A proposal lands only through the pull request and its gates. File: `src/components/views/ProposalReview.tsx`. | Test: `src/components/views/__tests__/ProposalReview.test.tsx::test_accept_requests_a_pull_request_and_offers_no_direct_write` (component). |
| `OVERSTORY-DECIDE-R009.3` | **Hot-path proof: reviewer decides a proposal.** Entry: the proposal route in `src/App.tsx`. The browser test signs in as a reviewer and lists proposals from a loopback arbora. It accepts one and observes the pull request link. It rejects one and observes the refusal. A second tenant sees no proposal of the first. Depends on: OVERSTORY-DECIDE-R009.2. | Test: `src/components/views/__tests__/ProposalReview.e2e.test.tsx::test_reviewer_lists_and_decides_a_proposal` (L4). |
| `OVERSTORY-DECIDE-R010` | **Artifact graph view (rollup).** The artifact graph view must show the next unblocked task. It must show the plan to reach a chosen goal or phase, and the open tasks in order. It must read them only through the intent operations of `ARBORA-OPS-R896.1`. Each task shows its row, its plan section and its contracts. The view computes no order and no state. Children `.1` and `.2` deliver it. Depends on: ARBORA-OPS-R896.1, MEDULLA-SDLC-R014.6. | Satisfied only when every child is satisfied. Root journey: `src/components/views/__tests__/ArtifactGraph.e2e.test.tsx::test_reader_follows_a_goal_to_its_open_tasks` (L4). |
| `OVERSTORY-DECIDE-R010.1` | **Render the answers of the served operations.** The view must render the answers for `next task`, `plan for goal G` and `plan for phase P` exactly as arbora returns them. It keeps the returned order. It labels an empty answer, a denied read and a transport failure as distinct states. File: `src/components/views/ArtifactGraph.tsx`. | Test: `src/components/views/__tests__/ArtifactGraph.test.tsx::test_answers_keep_order_and_states_are_distinct` (component). |
| `OVERSTORY-DECIDE-R010.2` | **Hot-path proof: follow a goal to its open tasks.** Entry: the artifact route in `src/App.tsx`. The browser test picks a goal against a loopback arbora. It observes the open tasks in the returned order, each with its row and contracts. Depends on: OVERSTORY-DECIDE-R010.1. | Test: `src/components/views/__tests__/ArtifactGraph.e2e.test.tsx::test_reader_follows_a_goal_to_its_open_tasks` (L4). |
| `OVERSTORY-DECIDE-R011` | **Project mode control.** The project view must show each project's mode: `reference`, `development` or `evolving`. A change must go through the manage operation of `ARBORA-OPS-R896.2`. A change to `evolving` must show the pending operator approval that arbora returns. The control never approves its own request and never sets the mode directly. Depends on: ARBORA-OPS-R896.2, MEDULLA-SDLC-R012.8. File: `src/components/views/ProjectMode.tsx`. | Test: `src/components/views/__tests__/ProjectMode.test.tsx::test_evolving_shows_pending_approval_and_never_self_approves` (component). Test: `src/components/views/__tests__/ProjectMode.e2e.test.tsx::test_mode_change_round_trips_through_arbora` (L4). |
